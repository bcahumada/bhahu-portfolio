CloudCommerce — Serverless Inteligente

Módulo 8 · AWS Academy Learner Lab · Aplicación sin servidor de extremo a extremo

Una tienda de e-commerce sin un solo servidor que administrar. El frontend estático se sirve desde S3, API Gateway es la única puerta de entrada, dos funciones Lambda —una para usuarios y otra para pedidos— concentran la lógica de negocio, DynamoDB persiste los datos y CloudWatch Logs deja registro de cada invocación. Cada pieza escala sola y se paga por uso.

Decisiones de diseño

  • Sin servidores que administrar. Lambda ejecuta la lógica solo cuando llega una petición y escala con la demanda; se paga por uso, no por servidores encendidos.
  • Una función por responsabilidad. Separar “usuarios” de “pedidos” mantiene el código simple y permite evolucionar cada parte por separado.
  • DynamoDB (NoSQL). Base de datos gestionada, de latencia baja y escalado automático, ideal para acceso por clave sin administrar motores ni capacidad.
  • API Gateway como puerta única. Un solo punto de entrada para seguridad, control de acceso y versionado de la API.
  • Observabilidad incluida. CloudWatch Logs registra cada ejecución, lo que permite verificar el funcionamiento sin acceder a ningún servidor.

Del diseño a la prueba

  • Landing en S3. Sitio estático público servido desde un bucket, sin servidor web que mantener.
  • Funciones probadas en consola. La lógica de usuarios y pedidos se validó ejecutándola desde la consola de Lambda.
  • API verificada extremo a extremo. GET /usuarios respondiendo en el navegador y POST /pedidos devolviendo 201 Created desde Postman.
  • Persistencia comprobada. Los pedidos quedan efectivamente guardados como ítems en la tabla DynamoDB.

Reflexiones y aprendizajes
  • “Sin servidores” no significa “sin observabilidad”. Al contrario: como no hay ninguna máquina a la que conectarse por SSH, CloudWatch Logs pasa a ser la única forma de confirmar que cada invocación se ejecutó y qué hizo. La vuelve indispensable desde el primer despliegue.
  • La responsabilidad única se paga sola. Separar usuarios y pedidos en dos funciones permitió desplegar, probar y escalar cada una sin que un cambio en una afecte a la otra.
  • On-Demand elimina una decisión difícil. No tener que estimar capacidad de antemano fue especialmente valioso en un proyecto donde el patrón de tráfico real es imposible de predecir.
